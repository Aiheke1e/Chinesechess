# Chinesechess —— JJ 象棋屏幕识别与自动对弈实验

一个**屏幕感知型**中国象棋自动对弈程序：截取 JJ 象棋客户端画面 → 识别棋盘
→ AI 选招 → 自动落子，完全在外部进行（不改内存、不注入、不逆向）。

默认直播名称为用户确定的“豆包象棋”，账号独立运营。互动展示只显示头像与“观众名字：弹幕内容”，独立弹窗没有标题栏和系统按钮；拖动画面移动位置，拖动边缘或四角缩放。设置页控制弹出/收起和宽高，收起保留同一个窗口及其位置。设置页的“展示头像”可预览选择全部10张图片，也可上传 PNG、JPG、WebP，上传原文件会复制到本地 `work/avatars/` 保存，后台预览和独立弹窗同步切换。AI身份说明保留在账号简介及直播说明中。

抖音头像、昵称、简介和口播示例见 [账号包装](douyin-brand-kit.txt)，身份与内置头像由 `stream_brand.py` 管理。原有默认风格和开场词会在读取时迁移，自定义语气、房间、音色和观众昵称保留；修改包装不会切换实际模型或语音服务。

设置页使用同一张对齐表单：连接操作在顶部，对弈、互动展示和日志开关逐行排列，互动开关及状态文字整行已移除，互动展示尺寸和头像相邻，重复的头像工具菜单入口已移除。顶部预览可在工作台和设置页显示，顶部预览及独立窗口的开关统一放在设置页，工作台不重复放置展示按钮；切换页面保留显示状态。暂停按钮仅显示“暂停下棋”。

## 工作原理

```
┌────────────┐   ┌──────────┐   ┌────────┐   ┌──────────┐
│ JJ 象棋窗口 │──>│ 屏幕捕获 │──>│ 棋子识别│──>│ 棋盘状态 │
└────────────┘   └──────────┘   └────────┘   └────┬─────┘
                                                    │
                                           ┌────────▼────────┐
                                           │ Pikafish 引擎    │
                                           │ (UCI + NNUE)      │
                                           └────────┬────────┘
                                                    │ 走法
                                           ┌────────▼────────┐
                                           │ 自动落子(鼠标)   │
                                           └─────────────────┘
```

三模块解耦：
- `board.py`  —— 象棋规则状态机（走法生成 / 合法性 / 评估 / FEN）
- `pikafish.py` —— 唯一走棋引擎；负责 Pikafish UCI 通信、超时和进程清理
- `vision.py` —— Win32 窗口截图、棋盘几何检测、模板匹配识别（可换 YOLO 检测器）
- `play.py`   —— 人类化鼠标拖拽落子 + 主控循环
- `main.py`   —— 串起整条的入口
- `calibrate.py` —— 在真实客户端上标定几何、生成模板
- `simulator.py` / `verify.py` —— 无客户端时端到端验证（已通过）

## 识别方案（两种）

1. **零依赖模板匹配**（默认）：用 `calibrate.py --templates` 截 14 类棋子图当模板，
   每个交叉点做 `matchTemplate` 比对。优点：无需训练、即开即用；缺点：对界面缩放/
   换肤敏感。
2. **深度学习检测器**（可选）：`config.json` 设 `"use_detector": true`，用
   `YOLODetector` 接 ultralytics YOLOv8（检测棋子 bbox + 类别映射到 14 类）。
   优点：旋转/缩放/部分遮挡鲁棒；缺点：需标注训练数据。

## 当前推荐入口（ADB 模拟器）

项目目前实际使用的是 `control_panel.py` / `player.py`。它连接已经启动的安卓模拟器，支持红方或黑方在下方，并使用 `adb_geom.json` 保存当前棋盘几何。

最方便的启动方式是双击 `start.cmd`。首次使用时：

> 换电脑、重新下载或需要补齐 Pikafish/ADB 时，请先看 [运行文件清单](运行文件清单.md)，里面有直接下载链接、放置路径和完整启动步骤。

1. 在 JJ 象棋中打开标准初始棋盘。
2. 点击“自动标定”。换分辨率、缩放或皮肤后也要重新标定。
3. 保持“只读检查（不点击）”勾选，点击“运行一手”，核对识别的 FEN 和建议走法。
4. 核对无误后取消只读，点击“运行一手”做一次真实落子测试。
5. 确认落子成功，再点“开始自动”。点击“停止”会立即终止当前对弈及其 ADB、引擎子进程，取消棋盘识别、自动接管、延时重启和待播棋局语音。再次开始时会重新核对最后保存的可信棋局。

### 桌面一键助手

桌面快捷方式“JJ象棋一键助手”会通过 `assistant_bootstrap.py` 启动控制面板：

1. 自动启动雷电模拟器（如果尚未启动）。
2. 自动打开 JJ 象棋（如果当前不是 JJ）。
3. 等待用户进入标准新棋或结构合法的残局；大厅和结算页不会触发点击。
4. 连续两次确认同一棋盘后，自动关闭只读模式并启动对弈。残局可在控制面板选择当前轮到红方或黑方；“自动判断”不唯一时默认红方。

模拟器路径和 JJ 包名可在 `assistant_config.json` 中修改。需要终止时点击控制面板的“安全停止”。
启动器会阻止重复运行，并把启动异常记录到 `work/assistant.log`；控制面板运行日志位于 `work/control_panel.log`。

### 直播讲解与弹幕互动

桌面控制台保留“工作台”和“设置”两个页面。顶部仅保留“开始下棋”和“暂停下棋”；F8可暂停下棋，取消识别、对弈和待播棋局语音，弹幕互动独立控制。设置页只保留“连接直播间 / 断开直播间”和“开启互动 / 暂停互动”两个常用操作按钮，连接中同一按钮变为“取消连接”，取消后旧请求不会重新连上。其余有开关状态的选项按行对齐，统一绿色开启、红色关闭：自动连局、解说、语音、沙盘、延伸讲解、顶部展示、独立展示和三个日志。欢迎及礼物沿用原有配置，设置页不再显示这行开关和互动状态。一次性操作仍在工具菜单内。

设置使用连续表单，不再拆成四块卡片。工作台显示棋局记录、解说记录、直播间消息三个日志，在“设置 → 功能开关”可独立隐藏，隐藏后其余栏自动平分空间，记录继续保留。直播间消息默认隐藏，连接成功后自动展开并同步开关；同一次连接中手动隐藏后不会反复弹出。关闭独立展示窗口时，对应开关也会恢复关闭。

界面默认使用“雾蓝柔光”主题：灰蓝底色、圆角表面和轻柔阴影。每栏右上角的“···”菜单提供跟随、回到最新/跳过旧播报、清空显示。设置修改即时生效，也可在“设置 → 工具 → 保存设置”手动保存。首次升级切换到新外观并恢复不透明窗口，之后保留用户选定的主题；原有主题仍可选择。圆角与阴影只在窗口尺寸或主题变化时重绘，不参与识别或落子循环。

棋局记录显示实际走法与运行反馈；解说记录汇总所有实际播报台词，包括讲棋、弹幕回复、礼物答谢和进场欢迎，逐条标明时间、对应走法或观众昵称。直播间消息单独显示连接器收到的观众原始弹幕、礼物及连击数量、进场、点赞和关注/分享事件，不受语音抽选、互动暂停或停止播报影响，也不会把原始消息混入口播记录。消息按批次刷新，保留最近2000行，待刷队列最多3000条，避免繁忙直播间拖慢控制按钮；切换房间后不显示旧连接的迟到消息。

互动展示的头像始终保留，仅在对应弹幕回复实际起播时显示原始昵称与弹幕，语音播完立即清空文字；生成中、未抽中的弹幕和礼物原始消息不提前占用文字区。纯文本测试保留约6秒供阅读，过时的清空任务不会影响下一条。礼物答谢直接使用“感谢××老板送的××，谢谢老板”，连击仍按接入数量合并，不调用模型、不加其他包袱。

互动先核实当前问题：丢子、抓炮、叫杀、局势和输赢等棋评优先使用只读棋局事实，信息不足时澄清，不附和观众的一句话来宣布优势或胜负。购买来源、品牌和人物称号没有资料时明确说无法确认，呼叫别人不编多角色对话。缺少主语的短口令不参加抽选，完整问题与纠错保留；“好嘞、哈哈”等常用开头按最近实际播出的正文去重，观众昵称不作为口吻话题。普通社交不硬加棋局、对手和风险等套话。

部分直播间的游客推送没有礼物，弹幕正常也不代表礼物接入完整。需要接收礼物时，在“设置 → 工具 → 登录抖音（接收礼物）”打开专用浏览器窗口，在抖音官方页面完成登录；保存后自动重连当前直播间。登录状态通过当前Windows账户的DPAPI加密保存在本机，HTTP和WebSocket连接都携带登录信息，不进入配置、日志或进程命令行。连接状态会区分“游客接入”和“已载入登录信息”；后者只说明已使用本机登录信息，是否收到真实礼物仍以实际推送为准。“清除抖音登录”会断开连接并移除保存的登录信息。

- 引擎分析会给每步计算“讲解重要度”。开启棋局解说与语音后，通常先准备对应走法的短播报，Windows 接受音频播放、拿到本手起播确认后才点击棋盘。弹幕互动正在生成或播放时，允许取消尚未起播的普通走法解说并继续落子，不延长45秒等待，也不事后补播旧内容；取消标记必须成功写入。已验证的一步取胜仍改为绝杀长解说，整段说完后落子。没有互动时，正常语音启动超时仍为15秒，失败暂停且不落子。
- 主播台可选“安静 / 自然 / 热闹”三档解说密度。默认“自然”：连续安静或数个普通回合后，只在等棋空档补充一段局面思路；新局面出现会丢弃过时解说。
- “游戏内沙盘”复用 Pikafish 已算出的合法主变化，不发起第二次搜索。关键交换、吃大子、将军应将及解将衔接在普通评分下也可演示，不只依赖高优势或绝杀；只吃子后闲走、循环局面和没有可核实结果的半段交换不演示。普通路线按战术链结束位置选取2–8次落子，包含回吃及应将，不固定截三步；常规尝试至少间隔3个己方回合及25秒，相同已展示路线150秒内不重复。对手快速走出路线第一步时，可核对新局面后衔接剩余步骤。完整将死路线在真实落子前预演，最多14个动作（含最后仅供沙盘的吃将/帅动作）。时间按路线长度和分段台词估算，普通演示最多30秒、绝杀最多42秒，异常超时只记未完成。进入、每步执行及返回实战分别验证；返回失败暂停，所有模拟动作只修改私有棋盘副本。
- 沙盘按“看点→每一步→结果”分别预热台词：本步语音实际开始后执行对应动作，语音说完再继续下一步；末步确认后再总结交换和代价。起播和完成回执与真实落子确认隔离，未准备好、取消、暂停或超时即结束演示并取消余下台词；语音关闭时同步展示文本，不等待TTS。日志标明沙盘步骤及结果，弹幕不能插入已进入沙盘的分段讲解。
- 棋局解说、弹幕互动及沙盘同时开启时，短交换可偶尔变成“主播提问→假设接法→沙盘看后手”的桥段。第8个己方回合后每盘最多尝试一次，前后至少间隔180秒；仅挑不亏子的合法路线，将杀、防守解将及明显劣势不触发。提问说完才尝试进入沙盘，不等待观众答案；台词使用实际招名与吃子对象，轮换提问和总结，不伪造观众发言。问句占用普通演示的时长预算，取消或局面变化即放弃，真实走法和落子确认沿用引擎流程。
- 讲棋、沙盘和互动共用TTS请求调度，同一时刻只发起一个合成请求，相邻请求至少隔0.5秒；当前走法、互动和绝杀优先于尚未发出的普通沙盘后续步骤。限流最多退避重试两次，暂停、过期或换步会取消尚未发出的请求，不继续合成旧棋谱；鉴权等其他错误不盲目重试。设置中的语音开关仍单独控制是否发声。
- 讲解优先说明解将、避开攻击和保护受攻棋子；有保护的低价值目标不当成可得子的进攻看点，同一个攻击目标近期讲过后只报新的实际走法。沙盘分步补充将军、解将和回吃，结果使用“一匹马、一门炮”等自然称呼。绝杀长台词说明杀法及核实过的将帅退路，减少泛泛的庆祝铺垫；已确认的兑子不再记成“丢了大车”。
- 开启棋局解说后，每完成3盘真实对局，在局间空档说一次“现在是北京时间×点×分，你看到的不是直播录像”，并在解说记录标为“北京时间”。按UTC+8读取实际准备播报时的时间，不调用模型编写；只读检查、暂停和重复结算不计盘数。新一局已开始、等待超过10秒或合成后已经跨分钟时跳过本次，不补播过时的报时。
- 关闭语音时沙盘只发送文本步骤，不等待任何语音回执；开启语音时，进入沙盘前核对本手分步讲解接口已就绪，旧界面进程不支持时跳过可选演示继续实战。引擎已发现对方将杀路线时暂停普通沙盘，播报优先说明防守，后续不反复用攻击目标掩盖险情。
- 引擎接收本盘起始可信FEN及双方所有已确认着法，断点恢复同时恢复历史；沙盘模拟和被拒绝的点击不会写入棋谱。重复局面中再次将军或追车马炮的非吃子着法会提前排除，减少等JJ长捉提示后才被迫换招；普通安静往返不因此禁走。不同新局或无法核对的历史重新建立起点，不能混入上一盘。
- 直播解说和战术沙盘默认开启（TTS 仍由“开播语音”单独控制）。沙盘计分实测平均约 0.01 ms，动画使用 Tk `after` 分帧调度，语言模型和 TTS 使用后台线程；自动对弈运行在独立子进程，Windows 下设为略高优先级，补充讲解与动画在后台运行；没有弹幕互动时普通走法等待本手短播报的启动确认，已验证的一步取胜等待整段绝杀文案播放完毕。
- 语言模型通过智谱 OpenAI 兼容接口生成简短、可朗读的话术。密钥使用当前 Windows 账户的 DPAPI 加密，不写入项目源码和日志。
- 棋局短播报先说明当前走法及核实的作用；等棋时先补充新攻击目标、照应己方棋子、避开攻击或兵卒过河等事实，再考虑已有合法主线里的具体后续，不再把“吃子是为了吃掉棋子”当作解释，默认只讲实际选中的走法及其后续，不介绍其他候选或“两种走法差距不大”。补充讲解最多两句、56字，没有新事实就跳过，不用裸预测填空档；固定包袱至少隔两条普通走棋播报再使用。连续吃子或连续将军的说法须先核对已确认落子、实际应手和当前棋盘；不同候选的预测路线不会混用。这些台词直接从已有证据组织，不增加引擎搜索或模型请求。每条语音携带对应手数、走法和独立标识；新的可信走法出现时，取消旧局面的待播台词与补充讲解。沙盘讲解使用独立标识，不会覆盖或冒充真实落子的起播确认。预判只说“对手可能走……”，不使用猜、押或八成；应手吻合时自然接续路线，变招时围绕实际走法轻松接话，不再自夸猜中。普通走子的动作不在等棋空档重复复述，吃子、将军、解将和收官时，只讲当前走法及其后续，跳过上一手的预判回顾和玩笑；平稳回合的应手回顾按对手实际走法标注，不借用当前我方手数。回吃提示明确点出棋子，只有合法主线证明回吃本手棋子时才说“吃回”；确认终局且棋盘吻合后才具体描述最后的将死。
- 语音使用已有百炼云端 TTS，当前可切换 `Maia` 女声与 `longanyang` 男声。
- 弹幕自动抽选，不要求“问主播”等前缀，已有配置里的旧前缀也不再作为识别条件。在线少于50人时约15秒最多抽选一条，50～499人约18秒，500～4999人约24秒，5000人及以上约30秒；弹幕达到每秒2条或10条时，分别至少间隔24秒或30秒。没有在线数据时按弹幕速度调整，页面显示“待获取”，不把累计观看量当作在线人数。优先完整问题、没看懂和纠错；“3路、炮83、进马”等孤立短片段留在原始弹幕日志，不硬接成高招评价。
- 抽选在本地完成，不为每条弹幕调用模型。过滤重复、纯表情刷屏和链接广告，同一观众只保留一条新消息，并限制连续选中同一个人的频率；匿名观众共用占位编号时，结合显示昵称区分，避免不同观众互相覆盖。候选池最多60条，超过25秒的内容不再开始回复。每次只生成一条回复，未选中的内容不进入语音队列。
- 已验证的绝杀长解说优先；对弈期间按讲棋、沙盘和弹幕穿插安排。每滚动60秒最多3段互动（包括弹幕、欢迎和礼物），累计约20秒后暂停抽选，互动结束后至少留10秒空档。独立弹幕模式不使用讲棋配额。长期没讲棋时为有效棋局内容保留时段，沙盘实际进入后保护整段讲解，不被新弹幕盖住；临近结尾的短句尽量自然结束。普通落子不额外等待弹幕，切换房间继续取消旧回复。
- 每条弹幕回复仅使用当前选中的原文和主播风格，不带入其他观众的历史对话。昵称不交给模型解释话题，由程序统一添加一次真实可读称呼；含星号的昵称不猜测补全。涉及走法、漏杀或绝杀时使用最近确认的只读棋盘记录，明确招法会核对是否合法、是否一步将死；没有证据时不附和杀棋，不让观众的建议直接控制棋盘。关闭棋局解说不影响只读上下文，暂停下棋或对局结束会清理旧局面。解说日志保留选中原弹幕，其他未选中的消息仍只在直播间日志里显示。
- 顶部直播展示区空闲时留白，不显示“等待互动”或默认欢迎文案。回复实际开始播放时显示观众昵称和弹幕原文，正常播完后仍保留，直到下一条回复实际起播才替换；关闭语音时按实际文字回复更新并同样保留。暂停、取消、断开、切换直播间或停止后清空。在线人数放在后台监控栏，设置页不再显示互动抽选状态文字。生成中、未选中的弹幕、后来的其他弹幕和棋局解说不会抢占展示区。
- 进场欢迎最多每分钟一条，只说“欢迎某某进入直播间。”，不调用语言模型，不追加套话；弹幕或绝杀忙碌时跳过欢迎，超过10秒未播的欢迎丢弃。礼物连击在短暂合并后只答谢一次，排在弹幕回复之后。
- 说话风格用于弹幕回复等模型生成的话术，影响语气、措辞和幽默程度；棋力、选招、弹幕抽选与音色不由它控制。走棋短播报和绝杀长文案采用固定模板，不会自动跟随风格改写。

绝杀收尾由 `mate_patterns.py` 检查选中的合法走法，确认将死或困毙后才触发幽默长文案。开启沙盘且存在完整将死路线时，先在JJ沙盘演示完整路线，再尝试仅供演示的吃将/帅收尾；进入后的每一步都验证，吃将前额外确认仍在沙盘且终局一致。只有最后吃将已确认才记为演示完成；如果平台在将死时提前退出或不接受收尾，不再重试棋盘点击、不虚报吃将。困毙没有被将军的将帅，不能伪造吃将收尾。沙盘返回实战后，仍须等已验证的一步绝杀长文案完整播完才真实落子；失败或未能确认返回则暂停。普通将军、优势分和不完整的杀棋主线不冒充完整绝杀演示。

杀法参考目录采用[玩家整理的 JJ 17种绝杀特效](https://www.bilibili.com/video/BV1VJ4m1N7QU/)，不是官方公布的完整清单，也不复刻 JJ 内部识别规则。基本棋形可参见[杀法教学](https://www.xqarena.com/zh-hans/guides/checkmate-patterns)。同一终局可能符合多个名称，程序优先明确组合；证据不足就报“组合将杀”，不凭场上有哪些棋子硬套名称。

| 杀法 | 收尾配合及识别依据 |
| --- | --- |
| 马后炮 | 马作炮架，位于将前两格，并控制将旁的退路。 |
| 重炮 | 同线双炮，前炮为后炮作架。 |
| 钓鱼马 | 钓鱼位的马参与封路，车完成将杀；贴身车且马护车时优先列马车。 |
| 列马车（立马车） | 底线贴身车将军，马护住车并参与成杀。 |
| 双车错 | 重放上一手、实际应手与本手，证明两辆不同的车交替将军。 |
| 铁门栓（铁门闩） | 中炮参与牵制，底线贴身车或兵封门。 |
| 天地炮 | 中炮和底炮都参与成杀，底炮完成将军。 |
| 夹车炮 | 保守识别同线炮、车、炮且三子均参与成杀的棋形。 |
| 卧槽马 | 马到对方底象前一格，直接将军成杀。 |
| 八角马 | 马在九宫角与将呈对角，参与封路，配合车将杀。 |
| 侧面虎 | 马位于侧面虎位置并参与成杀，同侧车将军。 |
| 对面笑（白脸将） | 将帅不能照面的规则实质限制对方逃将。 |
| 闷宫 | 底线炮借士为架，宫心士和底士堵住应对。 |
| 闷杀 | 将周围的宫内相邻位置均被己方棋子挤住，外面的将军无法解除。 |
| 双将 | 同时存在至少两路将军，且对方没有合法应手。 |

| 海底捞月 | 将已离开底线，车在将背后将军，底炮护车。 |

直播配置保存在 `live_config.json`；互动事件日志位于 `work/live_events.jsonl`。抖音连接所需的外部连接器和独立运行环境位于 `D:\environment\shuzhiren`，不会把数字人依赖复制进象棋项目。

“直播间连接”支持完整分享文案、`v.douyin.com` 短链接、网页版直播间地址及数字房间号。点击后立即显示解析进度，解析和连接在后台执行；只有弹幕连接实际建立才显示“已连接”。解析期间点“断开”会取消本次请求，旧请求不会重新连上或覆盖新状态。连接器使用安装目录内的绝对路径读取 `sign.js` 和 `a_bogus.js`，不依赖象棋项目的工作目录；缺少文件、依赖、网络超时等错误会显示在连接状态里。连接负责接收互动，自动回复还需开启“观众互动”；画面和解说声音由直播软件另行采集推流。

工作台顶部是面向观众的独立展示区，只保留昵称和弹幕，大字显示、按长度与宽度自动换行及调整字号。点击“弹出展示”可打开独立的“直播互动展示”窗口，用于单独采集；内容与主界面同步，窗口保持不透明，不显示人数、按钮、运行状态或分析信息。关闭再打开不会累积变量监听。
顶部“开始 / 暂停（F8）”下方是一条紧凑的后台监控栏：对弈显示当前进程的真实阶段与心跳；语音区分准备、播放、待播和暂停，并显示队列数量；直播显示连接状态、在线人数和弹幕速度。开启语音不等于已经播放，旧进程的心跳不会当作当前任务，安静的直播间也不会被误判成断线。所有复选框统一为状态开关：绿色、圆点在右表示开启；红色、圆点在左表示关闭，禁用时显示灰色，支持鼠标与键盘操作。

直播时可在设置中“弹出展示”单独采集观众画面，再“收起预览”腾出后台记录空间；收起只改变布局，不中断展示窗口更新，并记住上次选择。控制区显示本次已确认落子和完成局数。连接超时、播报失败、识别复核或心跳停滞时才展开异常提醒，可在“设置 → 工具 → 当前异常”查看各项原因；每个模块恢复时只清除自己的提醒。详情内容随状态变化更新，不在健康状态下常驻一排告警卡。监控只读取现有心跳、播放状态和队列，不增加模型或TTS请求。互动暂停时仍可统计收到的弹幕，但不抽选或回复。

工作台的日志按当前显示数量均分空间；清空显示不会删除日志文件，滚动条在无需滚动时淡出。预览一手、刷新、标定、体检、截图、缓存清理和当前异常详情集中在设置页的“工具”菜单。页面保存不会覆盖未展示的高级配置，独立展示窗口始终不透明。

等待对方落子时采用最近三帧的棋盘占位多数结果。单帧高亮、移动动画或模板漏识别不会立即改变可信局面；只有连续画面与合法走法能够互相印证时，程序才会推进棋局状态。

正常对局还会优先使用“变化格快速识别”：将当前画面与上一张可信画面对比，只定位变化最大的交叉点，再由象棋规则从合法走法中反推唯一的起点和终点。候选走法仍须通过局部棋子复核和连续两帧确认，选中高亮不会被当成落子；无法唯一判断、全屏动画或弹窗出现时会自动退回完整90格识别。自己的落子确认同样先检查起点和终点，完整全盘识别作为异常兜底。

主控制台默认显示精简对局摘要，只保留走法、局势、确认耗时、识别告警和胜负结果。每一手棋以虚线分隔成独立区块，正式棋谱使用更大字号；红方走法用暖红色、黑方走法用高对比蓝色，等待和确认信息则弱化显示，扫一眼即可分清双方。引擎坐标、候选路线、点击坐标等技术信息仍完整记录在 `work/control_panel.log`，方便故障分析但不会挤满直播界面。

对弈子进程会持续写入 `work/runtime_status.json` 心跳，控制台可以区分“等待对方”、“引擎思考”和“落子确认”。心跳停滞时会自动截图；只有在没有未确认点击的安全阶段才会自动重建对弈进程，落子核对阶段不会盲目重试。控制台日志达到 2 MB 后自动轮换，棋局事件与直播事件达到 8 MB 后轮换，各保留最近两份历史。UI 只保留最新的必要行数，长时直播不会因文本无限累积而越来越卡。

每次确认落子后，程序会把可信 FEN、轮次、朝向和移动棋子位置保存到
`work/session_state.json`。点击“停止”会直接中止当前任务，不再继续截图、识别或点击结算页面。再次点击“一键准备并等待新棋”或重新打开桌面助手，会优先核对并恢复该可信棋局；停止前后发生的走法能唯一推导时，会自动补入后继续。

本局确认胜负后，程序会优先通过安卓文字节点查找“继续、再来一局、再来一盘、下一局、确定”；
若 JJ 使用纯游戏画布，则只在已确认胜负的前提下检测结算页下半部的大型绿色按钮。
它也会连续关闭“快速升级”“段位保护”等视频奖励弹窗，不会点击“领取”广告按钮。
点击成功后控制面板会重新进入等待状态，下一局棋盘出现后继续接管。

先做只读检查，不发送点击：

```powershell
py -3 player.py --once --dry --engine pikafish --movetime 500
```

只读模式永远只预览一手，不会点击棋盘。`initial_turn` 表示启动程序时该谁走；新开标准对局固定为 `r`，即便程序执黑也不要改成 `b`。

主控现在采用以下保护：

- 启动局面必须连续两帧一致，并通过棋子数量上限、双王和行棋合法性检查。
- 等待对手时只接受能由当前可信局面唯一推导出的合法一步。
- 落子前再次核对整个棋盘；一次走子只发送一组起点/终点点击。
- 点击后轮询确认完整的预期局面。确认失败立即停止，不重复点击。

当前 1920×1080 的 JJ 标准棋盘已经完成真实闭环验证：识别标准开局、红方落子、识别黑方回应、红方再次落子均成功。

每次运行还会追加写入 `work/events.jsonl`，包含 `position`、`move_selected`、`move_applied`、`opponent_move`、`end` 等事件。后续 TTS、走法讲解和直播弹幕模块可以直接消费这个 JSONL，不必侵入下棋主循环。

## 象棋引擎

项目只使用随项目提供的 Pikafish，不再包含 Python Alpha-Beta 备用引擎。Pikafish
启动或计算失败时主控会安全停止并显示错误，不会悄悄切换到不同棋力的实现：

```json
{
  "engine_mode": "pikafish",
  "engine_path": "engine_bin/Pikafish-Windows-x86-64-universal.exe",
  "think_depth": 10
}
```

主控会把当前局面转成 FEN 发给 Pikafish，解析 `bestmove` 并通过合法走法校验后落子。

## 稳健性要点

- 用 `ctypes` 直接抓窗口 DC，减少全屏截图带来的坐标和多显示器问题。
- 落子支持分步拖拽（`play.click_drag`）。
- 轮次判定基于识别出的 `turn` 字段，避免抢拍/误触。
- 真实环境建议：先小范围人工核对 `calib_visual.png` 的交点是否对齐棋子中心；
  若界面缩放变化，重新跑 `calibrate.py`。

## 已知限制

- 当前几何/模板针对当前 JJ 棋盘皮肤与 1920×1080 模拟器；环境变化后必须重新运行“自动标定”。
- 模板方案对动态特效（选中高亮、最后一步标记）可能误判，可在 `extract_square`
  里加 mask 或改用检测器。
- 未处理“认输/和棋/网络断开”等弹窗；遇到无法推导的画面会超时停止。
- 不负责从 JJ 大厅自动匹配、报名或处理金币/奖励页面；请人工进入一盘新棋后再启动。
- 识别模板只适用于当前棋盘皮肤、分辨率和朝向；换肤、旋转棋盘或改变模拟器分辨率后必须重新标定。
- 正式长将、长捉与自然限着规则尚未实现。
